Beauty E-Commerce Site

A front-end e-commerce concept for AGL (Alexa Glow London), a fictional beauty brand, built as the summative assignment for my Web Development module. Visitors can browse products by category, open a product to see its full description and shades, add items to a bag, and go through a complete mock checkout, all running client side with no backend.

The Goal

Build a working online shop front for AGL, a fictional beauty brand: visitors should be able to browse products by category, open a product to see its full description and ingredients, add items to a bag, adjust quantities, and go all the way through a mock checkout, entirely in the browser with no real backend or database.

The Brief

Summative assignment for the Web Development module: design and build a front-end e-commerce site with a homepage, a filterable product catalogue, a persistent shopping bag, and a full checkout flow, styled with a visual identity (gold accents, elegant serif display type) that actually feels like a beauty brand rather than a generic template.

My Approach

  1. Planned the user flow: home → category → product detail → bag → checkout → confirmation, before writing any code.
  2. Built a 16-product catalogue across four categories (Skincare, Makeup, Hair Care, Beauty Tools), with category filter buttons that work together with a live search bar.
  3. Designed a gold, elegant visual identity for the brand: a serif display font for headings paired with a clean sans-serif body, and a warm gold and cream palette instead of a generic template look.
  4. Built product detail modals with an image zoom, a features checklist, ingredient tags, and keyboard-accessible shade swatches for products with more than one option (foundation, lipstick, mascara).
  5. Implemented the bag in vanilla JavaScript, persisted with localStorage so it survives a refresh or a trip between pages, with a live subtotal, total, and free-shipping progress bar.
  6. Built the checkout flow: a validated billing, delivery, and payment form that generates a mock order number and redirects to a confirmation page.
  7. Audited the site with Lighthouse and fixed what it flagged, covering accessibility, performance, and semantic structure.

Key Features

  • 16 products across 4 categories, with category filters and a live search bar that work together, including a "no products found" state.
  • Product modals with image zoom, a features checklist, ingredient pill tags, and shade swatches that update the product photo as you pick.
  • A shopping bag persisted with localStorage, with live totals and a free-shipping progress bar.
  • A full checkout flow with client-side validation, a generated order number, and a confirmation page.
  • Accessible by design: semantic HTML, descriptive alt text, ARIA labels on icon-only buttons, visually-hidden form labels, and keyboard-operable modals and swatches.
  • Mobile-first responsive layout with a sticky nav, dropdown menu, and mobile hamburger menu.

Challenges and how I solved them

A link that relied on colour alone

Lighthouse flagged the "Privacy Policy" link inside the newsletter text: it only picked up an underline on hover, so the rest of the time it looked identical to the surrounding paragraph, which fails for anyone who can't rely on colour contrast to spot it as a link. I made the underline permanent, with only the colour shifting on hover, so it reads as a link at every moment rather than just when a mouse happens to be over it.

A skipped heading level

The four category shortcut cards jumped straight from the page's h1 to h3, skipping h2 entirely, which breaks the outline that screen reader users navigate by even though nobody would notice it visually. I changed those headings to h2 so the page reads h1 → h2 → h3 with nothing skipped, and kept that same order when the cards later moved onto the home page under a "Shop by Collection" heading.

Fonts and icons blocking the first paint

Lighthouse scored cart.html at 79 for performance, mostly down to render-blocking requests. The fonts were being pulled in through an @import inside the stylesheet, which forces the browser to fetch and parse the whole CSS file before it even discovers the fonts are needed, turning a parallel download into a slow chain. I moved the fonts into <link rel="preconnect"> tags in the page head and switched Font Awesome to a non-blocking load pattern, which took performance up to 96 without changing how anything looks.

Results and what I learned

The finished site delivers a full front-end shopping experience for a fictional beauty brand, from browsing and filtering a 16-product catalogue to a persisted bag and a validated mock checkout, without a single line of backend code. Auditing it with Lighthouse and fixing what it flagged (a colour-only link, a skipped heading level, and render-blocking font and icon requests) took products.html to 100 for accessibility, best practices, and SEO, and pushed cart.html's performance score from 79 to 96.

It sharpened my eye for the kind of accessibility and performance issues that don't show up just by looking at a page, and reinforced good habits around semantic HTML, ARIA labelling, and how resource loading order affects real load time.
